# Web MultiSelect 2.6.0-rc03 — Release Notes

**Released:** 2026-10-22 · **Pre-release** (`npm install @keenmate/web-multiselect@rc`)

These notes cover the changes since **2.6.0-rc02**. Upgrading from 2.5? Read the
[2.6.0-rc02 notes](2.6.0-rc02.md) first. The theme: a **keyboard form flow** for single-select
(Tab picks, reopening starts at the value, no stale search), and a focused row you can actually
see.

The exhaustive, per-change list is in
[`CHANGELOG.md`](https://github.com/keenmate/web-multiselect/blob/prod/CHANGELOG.md) (section
2.6.0-rc03); this document is the upgrade guide and the highlights.

## Upgrade checklist

**Single-select users**

- [ ] **The search term is cleared when a single-select closes.** If you rely on reopening it
      with the previous term still filtering the list, set `should-keep-search-on-close="true"`.
      ([details](#single-select-clears-its-search-on-close))
- [ ] **Tab now selects the highlighted option.** Typing `brn` and tabbing away picks `Brno`
      and fires `select` / `change`. To keep Tab as "leave without picking", set
      `tab-behavior="close"`. ([details](#tab-can-select-tab-behavior))

**Theme authors**

- [ ] **The keyboard-focused option has a fill again.** If your theme relied on the transparent
      focused row from rc01 / rc02 (`--base-focused-bg`), set `--ms-option-bg-focused` instead —
      the component no longer reads `--base-focused-bg`.
      ([details](#the-focused-option-is-filled-again))

**Multi-select users**

- [ ] Nothing required: multi-select defaults are unchanged (search kept on close, Tab selects
      nothing, no initial highlight).

## Behaviour changes

### Single-select clears its search on close

`should-keep-search-on-close` used to default to `true` for every picker. In a single-select the
term is finished once a value is picked or focus leaves, so keeping it only got in the way: in a
cascade of selects, tabbing back into a field showed the old `cesk` in the box and a filtered list
you had to clear first. The attribute is now tristate:

| `should-keep-search-on-close` | single-select | multi-select |
|---|---|---|
| unset (new default) | **cleared** | kept |
| `true` | kept (the rc02 behaviour) | kept |
| `false` | cleared | cleared |

### The focused option is filled again

2.6.0-rc01 marked keyboard focus with the shared contract's 1px inset ring and no fill, as in the
tree components. In a combobox the focused option is what Enter / Tab will pick, and with a single
result the ring sat on the panel border — nothing looked highlighted. `--ms-option-bg-focused` now
defaults to the hover fill (`--ms-option-bg-hover`) under the ring, and deliberately does not read
`--base-focused-bg`. This is a documented exception to the shared item-state contract
(`docs/theming.md`); selected rows still follow `--base-selected-*`.

## New features — keyboard

### Tab can select: `tab-behavior`

What Tab (and Shift+Tab) selects with the dropdown open, before focus moves on as usual:

| `tab-behavior` | Tab selects | e.g. type `cesky kru`, Tab |
|---|---|---|
| `select-highlighted` | the highlighted option, including the first match highlighted while typing | Český Krumlov |
| `select-navigated` | only an option the user moved to (arrows, PageUp/PageDown, Home/End); typing resets it | nothing — press ↓ first |
| `close` | nothing (the 2.5 / rc02 behaviour) | nothing |

Unset: `select-highlighted` in single-select, `close` in multi-select.

- Tab only ever **adds**: an already-selected option stays selected, so Tab never un-picks in
  multi-select.
- A Tab selection is a normal selection: `select` / `change` fire, the form value updates, and a
  `beforeSelectCallback` veto still applies (the dropdown closes anyway; the value is unchanged).
- New type export: `TabBehavior`.

### Single-select opens at its value

Opening a single-select with no search term (Tab in, click) highlights the selected option and
scrolls it to the middle of the list, like a native `<select>`. With Item 30 of 50 selected,
ArrowUp goes to 29 and ArrowDown to 31, instead of starting from the top.

- The scroll is instant and moves only the list, never the page. With virtual scrolling the row
  is rendered first.
- Typing still highlights the first match.
- Tabbing straight through changes nothing (the highlighted option is already selected).

Try both in the **DA05 cascade** example (`examples-data-api.html`): it has controls for
`tab-behavior` and `should-keep-search-on-close`, and plain fields before and after to tab
through.

## Internal

Search normalization, matching and highlight mapping now come from
`@keenmate/web-components-core/search` (core 1.0.0-rc14), so other Keenmate components
(web-treeview next) match and highlight exactly the same way. `src/search.ts` is gone;
`normalizeSearchText` and the search types (`SearchBehavior`, `SearchMatch`, `SearchTermContext`,
`PreparedSearchTerm`, `SearchEntry`, `SearchCallbackContext`) are re-exported under the same
names. No API or behaviour change; the bundle size is flat.
