Basic Usage

The essentials, each as ONE live picker you configure with control switches — selection & input mode, content & display, groups, the scroll-to API, and search — plus a declarative, no-JavaScript setup.

Icons and subtitles on the option rows, plus how the current selection is shown in the control: the badges-display-mode and where badges sit (badges-position).

selected-order: selected badges reorder; the value stays as-picked

Reserved icon gutter. When only some rows carry an icon, the icon-less rows pull their label into the gutter and the list looks ragged. Turn on reserve-icon-slot to keep a fixed-width icon gutter on every row, so all labels share one start column. It's option-level — the same knob works in tree mode.

BU03 · Groups

Group options under headers with a group member. Each group header shows a count of that group's selected items (in any mode — open the dropdown to see it). Turn on per-group select-all (group-select-mode="cascade") to also put a tristate checkbox on each header that toggles the whole group — the group name is never itself a value. Turning on custom labels renders the header via renderGroupLabelContentCallback, whose ctx carries the per-group selection — here it writes GROUP — N remaining (selectableCount − selectedCount).

getCountLabelCallback: drives the in-input counter and each group's count

BU04 · Declarative Usage (No JavaScript)

For simple cases you don't need any script at all — put plain <option> / <optgroup> children inside the element and the component parses them once from the light DOM. It reads each option's value, its text, the selected attribute, and data-icon / data-subtitle. Single-select is multiple="false". Even custom styling stays script-free — the custom-styles attribute injects raw CSS into the shadow DOM (the declarative twin of getCustomStylesCallback).

No JavaScript — pure HTML. selected pre-picks an option.
Row icons from data-icon; the pill-shaped badges are pure custom-styles — no JS.
The <optgroup> label becomes the group header.
Second-line descriptions come from data-subtitle.
Show code 
<!-- Single-select, one option pre-picked -->
<web-multiselect multiple="false">
  <option value="yes">Yes</option>
  <option value="maybe" selected>Maybe</option>
</web-multiselect>

<!-- Grouped, with icons + subtitles + no-JS styling -->
<web-multiselect custom-styles=".ms__badge { border-radius: 999px; }">
  <optgroup label="Frontend">
    <option value="js" data-icon="🟨">JavaScript</option>
    <option value="react" data-icon="⚛️"
            data-subtitle="A JS library for building UIs">React</option>
  </optgroup>
</web-multiselect>

BU05 · Scroll-to API — scrollToGroup / scrollToValue / scrollToIndex

Imperative commands that bring an option or group into view. Pair with open() for an "open + jump" gesture. They work in floating, mobile fullscreen, virtual-scroll and tree modes, and return false when the target isn't in the current filtered list. clearSearch() reveals a filtered-out option so you can then scroll to it.

scrollToGroup centers the group header.
Virtual mode scrolls by index math — the row need not be rendered yet.
scrollTo* return values log here…
Show code 
el.open();
el.scrollToGroup('backend');   // header centered (or the group's first row in virtual mode)
el.scrollToValue('redis');     // → false if filtered out by the current search
el.scrollToIndex(0);

// Reveal a filtered-out option, then scroll to it:
el.clearSearch();
el.scrollToValue('jp');

BU06 · Search

Filter mode hides non-matches; navigate mode keeps every option visible and jumps focus between matches (Ctrl/Cmd + ↑/↓). Add a search hint, require a minimum number of characters before searching, and debounce the query.

search-mode:

When to use each mode:

  • Filter: large lists you want to narrow down (product catalogs, user lists).
  • Navigate: quick selection from a known list (country / state selectors).

BU07 · Search matching — search-behavior & search-match

Two independent switches for the built-in search. search-behavior decides how text is normalized: normalized (the default) ignores case and accents, so cesky finds Český Krumlov; case-insensitive ignores case only; exact ignores nothing. search-match decides where the term must appear. Both are live: flip them with a term typed and the list re-filters in place. Each option's search value is normalized once and cached, not on every keystroke.

search-behavior:

Things to try:

  • cesky: matches under normalized; switch to case-insensitive and it's gone (česk still works).
  • brno with equals: only the whole value counts (and case doesn't), so brn finds nothing.
  • nad: contains / word-starts-with find the "…nad Labem" towns; starts-with finds nothing.
  • kralove: ends-with finds Hradec Králové; word-ends-with adds Dvůr Králové nad Labem.
  • ^(Ústí|Nové) with regex. Keep typing an unfinished pattern like ^(Ústí and the last valid result stays.

Regex skips normalization: the pattern runs against the raw text, so search-behavior doesn't apply. ^ces finds nothing; ^Čes does.

Show code 
<web-multiselect search-behavior="normalized" search-match="word-starts-with"></web-multiselect>

// live, e.g. from a page-level switch
el.searchBehavior = 'case-insensitive';
el.searchMatch = 'regex';

// the same normalization, for your own code
import { normalizeSearchText } from '@keenmate/web-multiselect';
normalizeSearchText('Český Krumlov');   // 'cesky krumlov'

BU08 · Preparing the term — getSearchTermCallback

getSearchTermCallback turns what the user typed into what search should look for. Return a string (used as-is) or a RegExp. Here part numbers are written with all sorts of separators; the callback turns ha-324/56 into a pattern that ignores them, so it finds HA 324-56, HA32456 and HA-324/56. Untick it to compare: plain search finds only the one written exactly that way.

Show code 
el.getSearchTermCallback = ({ term }) =>
    new RegExp(term.split(/[^a-z0-9]+/i).filter(Boolean).join('[^a-z0-9]*'), 'i');
// "ha-324/56" → /ha[^a-z0-9]*324[^a-z0-9]*56/i

// A returned RegExp is tested against the raw search value. A returned string is used
// as-is, so normalize it yourself (normalizeSearchText) to match the prepared values.
